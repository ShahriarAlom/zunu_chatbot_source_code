# Junu AI Chatbot: Production Deployment Guide

This guide describes how to deploy the Junu AI Chatbot (Junu) system in your hosting environment. It provides step-by-step instructions, configuration snippets, and technical references for developers.

---

## 1. Setting Up the Database Connections

### To-Do
1. **Grant Database Permissions:** Run the following SQL queries on your website database (MySQL) to grant the necessary read/write permissions to the chatbot database user:
   ```sql
   GRANT SELECT ON rdadmin_dev_realdealride.cars TO 'rdadmin_dev'@'%';
   GRANT SELECT ON rdadmin_dev_realdealride.car_bookings TO 'rdadmin_dev'@'%';
   GRANT SELECT ON rdadmin_dev_realdealride.car_price_discounts TO 'rdadmin_dev'@'%';
   GRANT SELECT ON rdadmin_dev_realdealride.car_reviews TO 'rdadmin_dev'@'%';
   GRANT SELECT ON rdadmin_dev_realdealride.users TO 'rdadmin_dev'@'%';
   GRANT SELECT ON rdadmin_dev_realdealride.faqs TO 'rdadmin_dev'@'%';
   GRANT SELECT ON rdadmin_dev_realdealride.payments TO 'rdadmin_dev'@'%';

   GRANT INSERT, UPDATE ON rdadmin_dev_realdealride.support_tickets TO 'rdadmin_dev'@'%';
   GRANT INSERT, UPDATE ON rdadmin_dev_realdealride.support_categories TO 'rdadmin_dev'@'%';
   GRANT INSERT, UPDATE ON rdadmin_dev_realdealride.reservation_modifications TO 'rdadmin_dev'@'%';
   GRANT INSERT, UPDATE ON rdadmin_dev_realdealride.booking_cancellations TO 'rdadmin_dev'@'%';
   
   FLUSH PRIVILEGES;
   ```
2. **Initialize the Chatbot Vector Database:** 
   * Create a MariaDB database named `realdealride_ai` on port `3307`.
   * On first container startup, the database schema is automatically applied using the startup script located at [deliverables/requirements/init-mariadb.sql](file:///j:/realdealride-chatbot/ai-chatbot-project/deliverables/requirements/init-mariadb.sql).

### Explanation
* **Website Database Access:** The chatbot needs query access (`SELECT`) to read car inventories, reviews, bookings, and active customer details in real-time. It requires modification access (`INSERT` and `UPDATE`) to submit support tickets, reservation modifications, and cancellation requests directly on behalf of users.
* **Chatbot Vector DB Schema:** The database requires tables like `kb_documents`, `kb_chunk_embeddings`, and `query_log` to run semantic vector lookups.
* **Vector Dimensions:** The vector columns (`kb_chunk_embeddings.embedding` and `query_log.question_embedding`) are configured with `VECTOR(3072)` to store high-quality embedding vectors generated by the Gemini model.

Use this method if your database passwords contain special characters (like `;`, `!`, `}`, `@`). The backend will automatically and securely URL-encode the values:

#### Explanation
* **Decoupled Configuration:** Defining separate environments for the website and chatbot databases ensures that the AI application can search vector memories locally while looking up production data on your main server.
* **Auto-Encoding:** Setting DB connection attributes individually prevents database driver crashes caused by unescaped special characters in standard URI strings.

### Step 2: Starting the Chatbot Services

#### To-Do
1. Build and start the services in the background using Docker Compose:
   ```bash
   docker-compose up --build -d
   ```
2. Verify that both the backend and database containers are active and healthy:
   ```bash
   docker ps
   ```

#### Explanation
* **Docker Isolation:** Starting services with Docker Compose mounts the Python FastAPI application and the MariaDB server inside isolated containers, mapping ports internally and protecting database files inside persistent storage volumes.

### Step 3: Database & Document Syncing

#### To-Do
1. Let the container complete the automated database schema verification and document ingestion on startup.
2. **Force Manual Ingestion (Optional):** If you ever need to manually force a cleanup and rebuild of your vector search database without restarting your containers, run this command:
   ```bash
   docker exec -it rdr_fastapi_backend python clean_and_reingest.py
   ```

#### Explanation
* **Automatic Schema Healing:** When the FastAPI container starts, it connects to MariaDB and checks the structure of the `kb_chunk_embeddings` and `query_log` tables. If it finds that they exist but are configured with outdated vector dimensions, it automatically runs `ALTER TABLE` commands to update the columns to `VECTOR(3072)` to match the Gemini model's outputs. This preserves existing tables and prevents database connection errors.
* **Automated Ingestion:** Immediately after verifying the database, the container launches the `clean_and_reingest.py` script. It scans the `/app/knowledge_Base_doc/` directory, checks for new or modified files, cleans duplicate entries, and embeds any missing documents using the Gemini API.
* **Free Tier Daily Quota:** The Google Gemini API key free tier limits embedding requests to 1000 requests per day. The automated ingestion script automatically handles and retries rate limit exceptions. If you exceed the 1000 daily limit, the remaining documents will fail with quota errors. The database retains the active ones, and you can safely restart the container or rerun the manual command tomorrow to pick up where you left off.

### Step 4: Setting Up the Web Server Redirects

#### To-Do
1. Open your Nginx site configuration file (typically located in `/etc/nginx/sites-available/default`).
2. Add this server block to route requests and WebSocket traffic to the chatbot backend:
   ```nginx
   server {
       listen 80;
       server_name yourdomain.com;

       # Chatbot Backend API Endpoints
       location / {
           proxy_pass http://127.0.0.1:8085;
           proxy_set_header Host $host;
           proxy_set_header X-Real-IP $remote_addr;
           proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
           proxy_set_header X-Forwarded-Proto $scheme;
       }

       # WebSocket Route (For Chat & Admin Takeover)
       location /ws/ {
           proxy_pass http://127.0.0.1:8085;
           proxy_http_version 1.1;
           proxy_set_header Upgrade $http_upgrade;
           proxy_set_header Connection "Upgrade";
           proxy_set_header Host $host;
           
           # Prevent connection timeouts for long-lived sockets
           proxy_read_timeout 86400s;
           proxy_send_timeout 86400s;
       }
   }
   ```
3. Test and reload Nginx to apply changes:
   ```bash
   sudo nginx -t && sudo systemctl reload nginx
   ```

#### Explanation
* **WebSocket Upgrades:** Standard web proxies drop persistent connections unless Nginx is explicitly configured to upgrade the `Upgrade` and `Connection` HTTP headers.
* **Timeout Prevention:** Setting `proxy_read_timeout` to 24 hours (`86400s`) keeps client connections active, preventing the browser widget from dropping and reconnecting repeatedly during periods of idle conversation.

### Step 5: Embedding the Chatbot on Your Website

#### To-Do
1. Copy the JavaScript file **`rdr_chatbot.js`** from `deliverables/frontend/` and place it inside your website's public assets directory:
   * **Location:** `realdealride.com/public/frontend/js/rdr_chatbot.js`
2. Integrate the widget into your layout template file (e.g., your Laravel Blade master layout `resources/views/layouts/master.blade.php`) by adding this script block inside the `<head>` tag. Ensure you include the `@if(Auth::check())` condition to dynamically generate and pass user details when logged in:
   ```html
   <!-- RealDealRide Junu Chatbot Integration -->
   @if(Auth::check())
       <script 
         src="https://yourdomain.com/frontend/js/rdr_chatbot.js"
         id="rdr-chatbot-script"
         data-websocket-url="wss://yourdomain.com/ws/chat"
         data-member-id="{{ Auth::id() }}" 
         data-jwt-token="{{ App\Helpers\ChatbotHelper::generateToken(Auth::id()) }}"
         data-guest-session-id=""
         defer>
       </script>
   @else
       <script 
         src="https://yourdomain.com/frontend/js/rdr_chatbot.js"
         id="rdr-chatbot-script"
         data-websocket-url="wss://yourdomain.com/ws/chat"
         data-member-id="0" 
         data-jwt-token=""
         data-guest-session-id=""
         defer>
       </script>
   @endif
   ```

#### Explanation of Script Attributes
* **`id="rdr-chatbot-script"`**: Required. A unique ID that allows the chatbot Javascript code to find itself in the webpage DOM, read these custom configuration attributes, and bootstrap itself.
* **`data-websocket-url`**: The WebSocket protocol address where the chatbot backend is listening for live chat conversations. Use `wss://` for secure connections over HTTPS.
* **`data-member-id`**: The unique database ID of the logged-in customer. In Laravel, this is output dynamically using `{{ Auth::id() }}`. If the visitor is a guest, this attribute must remain `0`.
* **`data-jwt-token`**: A cryptographically signed token generated by the website backend. The widget sends this token during the WebSocket handshake to verify the member's identity. It must be empty when the user is logged out.
* **`data-guest-session-id`**: Stored in the browser's local storage. This is passed when a guest logs in to merge their anonymous guest chat history and support tickets into their registered account.
* **`defer`**: Ensures the browser loads the script in the background and runs it only after the HTML document structure is fully parsed. This prevents errors by ensuring `document.body` exists when the script initializes.

## 3. Verifying which user is using the chatbot

This section outlines how to configure secure tokens, handle fallback guest sessions, manage dynamic logins, and structure WebSocket payloads.

### To-Do

#### Step 1: Create the User Token Generator Helper
Create a helper script in your website backend to generate signed JWT tokens. Below are implementations for Laravel (PHP) and Node.js:

##### Laravel (PHP) Helper
* **Where to save:** Create this file in your Laravel app directory at `app/Helpers/ChatbotHelper.php`.
```php
<?php

namespace App\Helpers;

class ChatbotHelper
{
    public static function generateToken($memberId, $guestSessionId = null)
    {
        // 1. Get the shared secret key from .env file
        $secret = env('JWT_SECRET');
        
        // 2. Define headers and authentication claims
        $header = json_encode(['typ' => 'JWT', 'alg' => 'HS256']);
        $payload = json_encode([
            'member_id' => (int)$memberId,
            'guest_session_id' => $guestSessionId,
            'iat' => time(),
            'exp' => time() + (24 * 60 * 60) // Token is valid for 24 hours
        ]);
        
        // 3. Encode fields to URL-safe Base64
        $base64UrlHeader = str_replace(['+', '/', '='], ['-', '_', ''], base64_encode($header));
        $base64UrlPayload = str_replace(['+', '/', '='], ['-', '_', ''], base64_encode($payload));
        
        // 4. Calculate signature using HMAC-SHA256
        $signature = hash_hmac('sha256', $base64UrlHeader . "." . $base64UrlPayload, $secret, true);
        $base64UrlSignature = str_replace(['+', '/', '='], ['-', '_', ''], base64_encode($signature));
        
        // 5. Combine and return the token string
        return $base64UrlHeader . "." . $base64UrlPayload . "." . $base64UrlSignature;
    }
}
```

##### Node.js Helper (using `jsonwebtoken` package)
* **Where to save:** Create this file in your utility helper directory, for example, `helpers/chatbot.js`.
```javascript
const jwt = require('jsonwebtoken');

function generateChatbotToken(memberId, guestSessionId = null) {
    const secret = process.env.JWT_SECRET;
    return jwt.sign(
        {
            member_id: parseInt(memberId),
            guest_session_id: guestSessionId
        },
        secret,
        {
            algorithm: 'HS256',
            expiresIn: '24h' // Automatically sets 'iat' and 'exp' claims
        }
    );
}

module.exports = { generateChatbotToken };
```

If your website uses AJAX or Single Page Applications (SPA) where pages do **not** reload upon login, your login controller should return the token and guest ID in a JSON payload. This allows the frontend script to receive the token dynamically and re-establish the WebSocket connection with authenticated permissions:

To connect, open a WebSocket connection and append the JWT token and parameters to the query string:
```
ws://yourdomain.com/ws/chat?session_id=verification_session_99&token=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...&member_id=22&guest_session_id=89ef6731-92fa-4cb5-b5f7-640be045f2ad
```

#### Step 4: Exchanging Real-Time Chat & Takeover Messages
Once the WebSocket is open, messages are transmitted as strings or JSON payloads depending on the event:

* **Customer Chat Message:** Sent as a plain text string.
  ```
  "Show me my reservation status"
  ```
* **Support Agent Takeover Notification:** Sent by the server as a JSON payload to notify the widget UI that a human agent has joined:
  ```json
  {
    "role": "system",
    "content": "System: A customer support agent has joined the chat and taken over."
  }
  ```
* **Support Agent Message:** Sent by the support agent to the user, formatted as a JSON payload to display in a distinct admin style:
  ```json
  {
    "role": "admin",
    "content": "Hello! I am checking your reservation details now. One moment."
  }
  ```

### Explanation

* **JWT Claims Breakdown:**
  * `member_id` (Integer): Identifies who is chatting to fetch their past bookings.
  * `guest_session_id` (String): Used to find and merge history when a guest logs in.
  * `iat` & `exp` (Integer): Issued-at and expiration timestamps to prevent old token reuse.
* **Zero Database Session Sharing:** The handshake requires no shared Redis, database connections, session tables, or user queries between Laravel and FastAPI. The chatbot backend validates tokens entirely in-memory using the shared secret.
* **Stateless Cryptography:** By signing claims with HMAC-SHA256, both backends achieve secure verification with zero network roundtrips. Laravel signs the JWT token, and FastAPI verifies it in-memory.
* **Fully Portable Handshake:** Because the authentication is token-based and stateless, the chatbot widget and connection logic are extremely easy to plug into any other website or backend technology without code modifications.
* **Fallback to Guest Session:** If the token signature is invalid, tampered with, or expired, the connection is **not** closed. Instead, the backend automatically downgrades the connection to a guest session (`member_id = 0`). This allows users to still chat and ask general FAQs without getting disconnected.
* **Session Hijack Protection:** If a guest attempts to connect to a specific `session_id` that is already associated in the database with an authenticated user, the backend automatically generates a new random `session_id` to isolate their connection, keeping private logs hidden.
* **Write Restrictions:** Guest sessions (including guest sessions where an email was entered manually in chat) are restricted from write actions (booking modifications or cancellations) to prevent identity theft. They are only authorized to ask questions and create support tickets.
* **WebSocket Takeover:** Real-time takeover is delivered over WebSocket JSON frames to ensure sub-second UI switches and persistent live agent messaging.

## 4. Connecting the Admin Panel to the Knowledge Base

This section describes how your administration panel can perform full CRUD operations on the chatbot's knowledge base using a 100% decoupled REST API, without sharing any database credentials or connections.

### To-Do

#### Step 1: Listing the Documents (Admin Dashboard)
Query the chatbot's REST API endpoint to retrieve and display a list of all active policy documents.
* **Where to place code:** Place this code inside the admin dashboard controller that renders the chatbot settings list view (e.g., `app/Http/Controllers/Admin/ChatbotController.php`):
```php
use Illuminate\Support\Facades\Http;

public function index()
{
    // Fetch all document records via the chatbot's REST API
    $response = Http::get('https://yourdomain.com/chat-api/knowledge');
    
    $documents = [];
    if ($response->successful()) {
        $documents = $response->json();
    }
    
    // Pass $documents to your blade view resources/views/admin/chatbot/index.blade.php
    return view('admin.chatbot.index', compact('documents'));
}
```

#### Step 2: Saving and Updating Documents (Admin Form)
When an administrator edits policy text or uploads a new plain text file, send a `POST` request to the chatbot's REST API endpoint. The chatbot backend saves the text and automatically handles background chunking/embeddings generation.
* **Where to place code:** Place this code inside the store/update form submission method in your admin controller (e.g., `app/Http/Controllers/Admin/ChatbotController.php`):
```php
use Illuminate\Support\Facades\Http;

public function savePolicyDocument(Request $request, $id = null)
{
    $title = $request->input('title');
    $text = $request->input('source_text');
    $version = $request->input('version', '1.0');

    // Trigger the decoupled REST API endpoint (sends document_id if updating)
    $response = Http::post('https://yourdomain.com/chat-api/knowledge', [
        'document_id' => $id ? (int)$id : null,
        'title' => $title,
        'source_text' => $text,
        'version' => $version
    ]);

    if ($response->successful()) {
        return redirect()->back()->with('success', 'Document saved and vector embedding started in background.');
    } else {
        return redirect()->back()->with('error', 'Failed to save document via REST API.');
    }
}
```

#### Step 3: Deleting Documents (Admin Form)
When a document is deleted from the admin panel, send a `DELETE` request to the chatbot's REST API. The chatbot database deletes the record and cascades the deletion to automatically purge all corresponding vector chunks.
* **Where to place code:** Place this code inside the deletion form method in your admin controller (e.g., `app/Http/Controllers/Admin/ChatbotController.php`):
```php
use Illuminate\Support\Facades\Http;

public function deletePolicyDocument($id)
{
    // Trigger the decoupled REST API delete endpoint
    $response = Http::delete("https://yourdomain.com/chat-api/knowledge/{$id}");

    if ($response->successful()) {
        return redirect()->route('admin.chatbot.index')->with('success', 'Document and all vector search memories deleted.');
    } else {
        return redirect()->back()->with('error', 'Failed to delete document via REST API.');
    }
}
```

### Explanation

* **100% Decoupled REST API Architecture:** The Laravel application communicates with the chatbot backend solely through HTTP REST endpoints (`GET`, `POST`, `DELETE`). This removes the need for secondary database configuration (`chatbot_db`), keeping the two applications isolated and secure.
* **Zero Database Session Sharing:** No MariaDB server ports or database credentials need to be exposed to the Laravel application.
* **Fully Portable:** The admin integration is completely independent of the chatbot's database technology. The chatbot container can be migrated or updated without requiring config changes on the website side.
* **Asynchronous Rebuilds:** The `POST /knowledge` REST API endpoint registers a background task in FastAPI to process document chunking and embeddings. This ensures the Laravel admin controller returns instantly without blocking the admin dashboard.
* **Cascading Delete Constraint:** The database schema has a foreign key constraint linking `kb_chunk_embeddings` to `kb_documents` with `ON DELETE CASCADE`. When a document is removed from `kb_documents` via the `DELETE /knowledge/{id}` endpoint, the database engine automatically cleans up all associated vector chunks, removing the document from the chatbot's active memory.
